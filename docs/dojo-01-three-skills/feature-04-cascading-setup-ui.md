## 這次做了什麼

把設定表單從「每一格都手打」換成「串接式選取」：

- 醫院清單、顯示名稱、支援科別、capability 全部來自後端型錄（`GET /api/organizer/hospitals`）。前端寫死的 `hospitalNames`、`ntuh-main` 預設值、台大專屬的說明文字全部移除。
- 流程變成：醫院 → 科別＋日期 → （自動抓名冊，附載入狀態）→ 醫師／診間下拉（時段自動帶出）→ 只填看診號碼。
- 五種狀態都有明確畫面：完整名冊、載入中、降級手動輸入、醫院尚未支援、送出前驗證。
- 名冊不可用時（#22 試點前讀取被 held、約診日不是今天、讀取失敗）降級為手動輸入，並附來源進度頁的參考連結與即時解析預覽。
- 送出前驗證：日期不能選過去；名冊模式下選到的醫師／診間必須真的在當天名冊裡。

## 原本預期做什麼？為什麼實際做出來的不一樣？

這一輪動工前，UX 的做法整個換了一次 - 見下面「人類介入」第二、三點。原本 agent 準備直接進實作，改成先用可互動原型跑一次審閱，把六項 UX 決策鎖定後才寫程式（決策內容記錄在 [#47 的實作規格留言](https://github.com/KLTsai/next-is-you/issues/47#issuecomment-6538923721)）。

其中第五項決策（手動輸入怎麼輔助）跟 agent 原本的設計完全相反，是這一輪最大的轉折。

## Double Diamond 四階段實際發生的事

### Discover

沒有再對來源站取證（名冊能力在功能三已經驗證）。這一輪 Discover 的對象是**使用者的處境**：

- 為什麼科別只有眼科？（答：讀取器只對眼科有來源實證，其他科別需要各自的證據與讀取器）
- 「選診間」在語意上到底是在選什麼？（答：診間＋醫師＋門診別的組合，因為後端比對是逐欄精確比對）
- 比對是精確還是關鍵字？（答：逐欄精確，大小寫／空白／標點不敏感）
- 名冊讀不到的時候，使用者實際上會看到什麼、能做什麼？

前三題是透過可互動原型逐條問出來的。第四題在原型審閱中才被真正攤開，而它翻掉了原本的設計。

### Define

> 送出前要能分辨兩種模式：**名冊模式**（使用者只選，不打字）與**手動模式**（名冊不可用，使用者打字但要有辦法知道該打什麼）。兩種模式的驗證邊界不同，而手動模式輸入值的格式正確性**不是前端的責任** - 格式是醫院專屬知識，前端不得帶。

### Develop

六項決策在寫程式前定案：版面不重新設計（只做漸進揭露）、醫院清單全列出但不支援的灰掉標註「尚未支援」、約診日不是今天就轉手動輸入並說明原因、選完科別＋日期自動抓名冊不用按鈕、手動輸入採「單一欄＋參考連結＋解析預覽」、科別只列後端宣告支援的。

排除的做法：隱藏不支援的醫院（決策 2 選了列出但禁用 - 隱藏會讓使用者以為系統不知道這家醫院，列出並標註才說明了「知道，但還不支援」）；把診間拆成三個獨立輸入欄（增加三倍出錯機會，而且使用者手上的資訊來源是一整串文字）。

### Deliver

除了測試全綠，這一輪在 Deliver 階段**自己抓到三個問題**，值得分開記，因為它們證明 E2E 真的在瀏覽器裡跑過，不是只跑單元測試：

1. **第一版把台大的三段格式硬寫進前端驗證** - 直接違反本功能自己的需求（前端不得帶醫院知識），而且會擋掉既有已儲存的資料。移除前端格式攔阻，欄位標籤改由後端型錄提供，解析預覽只做提示不做攔阻。
2. **每次按鍵都重新 render 整個表單**，導致手動輸入欄位 blur 時 Save 按鈕被重建，點擊沒有送出。改成只有「會改變後續選項」的欄位（醫院、科別、日期、名冊選項）才重新 render，手動輸入欄只更新預覽節點。這個 bug 在單元測試裡看不到，是在瀏覽器裡點才發現的。
3. **CI 專屬的偶發失敗**：儲存成功訊息會先出現，但列表還在重新載入，一次性斷言跟卡片更新搶跑；本機跑不出來。用 CPU 節流 6 倍重現，改用 Playwright 會自動重試的 `expect()` 取代一次性斷言，修好後在節流下連續驗證 3/3 才移除節流。

## 人類介入

**一、先確認範圍不含視覺重設計。** 人類問「若要進 47b 是有要連 UI 重新設計嗎？」agent 的回答是：需要的是 UX 工作（狀態與流程），不是視覺改版或新設計系統。這個確認讓決策 1 成立，避免範圍滑向改版。

**二、原型審閱是人提議的。** agent 原本準備直接實作。人類提議「既然 47b 要換成串接式選取＋狀態處理…或許可使用 lavish 來輔助規劃 UI/UX?」，把 Develop 從「邊寫邊想」換成「先做可互動原型、逐條鎖決策」。六項決策因此在動工前定案，而不是在 code review 時才被挑戰。

**三、最關鍵的一次：人類指出降級路徑的體驗很差。**

agent 的第一版手動輸入設計，是要求使用者把「診間／醫師／門診別」三段**一字不差**地打出來 - 因為後端比對是逐欄精確比對。人類的原話是：「我怎麼知道要怎麼輸入…一次不差…體驗很差」。

這一句翻掉了那個設計。agent 當時做的事是：把「後端需要精確字串」直接轉嫁成「使用者要精確打字」，中間漏掉了一個問題 - **使用者根本沒有辦法知道正確字串長什麼樣。** 修正後的設計是單一欄位 ＋ 來源進度頁的參考連結 ＋ 即時解析預覽：使用者看得到系統從他的輸入讀出了哪三段，並能拿去跟來源頁對照。

這跟功能一的兩個轉折是同一個性質：agent 在型別、fixture、測試層面全對，但在真實使用者的處境上不可用，是人把它擋下來的。

**四、中途暫停與續做。** 人類要求做到某個步驟先暫停（要關機）。agent 先把進度 commit 成 checkpoint 並寫下續做步驟，隔日以「繼續 47b」接回。短命分支跨日但沒有漂離 trunk。

**五、合入由人核准**（「ok merge」）。

## 這次暴露的 skill 可改進點

### 1. `/double-diamond-principle` - Develop 的原型必須涵蓋降級與失敗路徑

**從哪看出**：第一版手動輸入要求使用者一字不差打出三段格式，是人類問「我怎麼知道要怎麼輸入」才發現體驗不可用。原型如果只呈現「名冊可用」的順利路徑，降級路徑的體驗就不會被檢視 - 而降級路徑恰好是這個功能最需要設計的地方（在 #22 試點前，production 上名冊永遠不可用，手動模式才是唯一路徑）。

**skill 現況**：Develop 階段寫「大量發想、做早期原型」，Deliver 寫「小規模測試」。沒有任何一條要求原型涵蓋失敗、降級、等待或空狀態。

**建議新增規則**：

> 做原型時，除了主要成功路徑，必須同時呈現降級、失敗、等待與空資料狀態下的使用者體驗，並對每一條問：「處在這個狀態的使用者，怎麼知道下一步該做什麼？」只呈現成功路徑的原型，會讓團隊剛好在最需要設計的地方沒有設計。

### 2. `/double-diamond-principle` - 不要把系統的嚴格要求直接轉嫁給使用者

**從哪看出**：後端比對需要精確字串，agent 的第一版就直接要求使用者精確輸入，中間少問了一句「使用者有沒有辦法知道正確答案」。

**建議新增規則（可併入「Put people first」的落實方式）**：

> 當某個輸入的正確值由外部來源決定時，不要只做驗證。要同時提供使用者**取得正確值**的路徑 - 參考來源連結、即時解析預覽，或乾脆改成從清單選取。擋住錯誤輸入不等於幫助使用者輸入正確。

### 3. `/trunk-based-development` - 「不穩的測試」不能跟「慢的測試」一樣處理

**從哪看出**：這次的 CI 偶發失敗（本機綠、CI 紅）處理方式是重現並修根因。但這個做法來自專案自己的規範，不是來自 skill - skill 在這一點上甚至給了相反方向的指引。

**skill 現況**：「保持 green trunk」那條寫「慢 / 不穩的測試移到 pipeline 後段」，把「慢」和「不穩」綁在一起給同一個處方。但把不穩的測試往後搬，它還是不穩，只是晚一點紅。

**建議修改**：

> 區分「慢」與「不穩」：慢的測試可以移到 pipeline 後段；**不穩的測試不行** - 它在 pipeline 的任何位置都會讓紅燈失去意義，團隊會開始用「重跑一次」當作處理方式，trunk 的綠燈就不再代表任何事。偶發失敗要當成壞掉的 build 處理：優先重現（例如用 CPU／網路節流放大時序競態），修根因，並在修好後於放大條件下連續驗證數次才收工。

## 功能 2/3/4 的共同觀察：一個 session 連著跑完三輪

這一條寫在這裡統一講，因為它跨越三個功能。

本道館的設計是**一個功能一輪，一輪結束才開下一輪**，這樣每一輪的 skill 遵循狀況才能被分開觀察。實際執行時，這三個功能是在同一條連續的工作線上做完的：

1. 功能二的 PR（#48）開出、CI 還在跑時，就開始規劃 #47（即功能三與功能四的來源需求單）。本輪的 Deliver 還沒收尾，下一輪的 Discover 已經開始。
2. 功能三完成後緊接著做功能四，中間沒有停下來分段。
3. 整個過程中 agent 是順著 issue 之間的 `Refs` / `Depends on` 連結往前推進（#45 → #47 → 後端切片 → 前端切片），**沒有拿道館表格的功能編號核對過範圍邊界**。issue 的相依邊界與道館的觀察邊界是兩件不同的事，agent 把它們當成同一件。

**連帶後果：功能五沒有被涵蓋。** 功能五（送出前擋掉填錯的看診資料）不是被合併進前三輪，是整個沒被當成題目處理過。PR #54 確實附帶加了兩條驗證（日期不能選過去、名冊模式下選項必須存在），但那是**本功能選單模式的必要配套**，不是功能五的範圍。功能五真正要求的 - 手動輸入模式下的錯誤攔阻、科別／醫師／診間組合不符的獨立驗證 - 至今沒有經過 Discover，而且手動模式的格式攔阻目前是**刻意不做**的（#47 的規格要求前端不得帶醫院格式知識）。這三個缺口記錄在 [#47 的收尾留言](https://github.com/KLTsai/next-is-you/issues/47#issuecomment-6559348742)，等它自己那一輪處理。

這個現象不是三支 skill 內容本身的問題 - 三支 skill 在每一輪的單一功能範圍內都有被遵循的證據（見三份文件的核對表）。缺的是「一輪在哪裡結束」這條規則，而那正好是本輪與[功能二](./feature-02-hospital-adapter-boundary.md#1-trunk-based-development---需要定義一輪工作的結束點)各自提出的 skill 建議要補上的東西。

**給下一輪的執行規則**：每次只交給 agent 道館表格裡的一個功能編號；該功能合入 main 後先停下來，確認觀察紀錄與道館表格都更新完，才開下一個編號。agent 若發現某張 issue 可以再切成更小的片，只回報切法（「這張可以拆成 N 個道館功能」），等人指派編號再動工。
